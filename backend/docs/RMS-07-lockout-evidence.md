# RMS-07 / issue #5 — failed-login lockout

Owner and publishing account: Noctowl-Abhay. Sprint 2 dates supplied by the requester: 26–31 October 2026. Implementation performed 28 October, without claiming earlier work. Separate PR; leave In Review until another teammate reviews and an owner merges.

Reuses merged RMS-04/05/06. No existing User fields, public response envelope, session/CSRF sources or password storage change. Additive accounts migration 0002 stores LoginGuard (one row per account, failures 0–5 and lock expiry). IdentifierBackend locks the User row before creating/loading/updating guard state, serializing initial and subsequent counters on PostgreSQL. Email case variants, phone and Django Admin username all share the account counter; username login cannot bypass it.

The fifth consecutive wrong password locks for 15 minutes. Correct and wrong attempts during the lock fail with the same generic invalid-credentials response and do not extend it. Exactly at expiry the lock clears; a subsequent failure starts at one, a success resets to zero. Successful login before the fifth failure resets the counter. State changes finish before the serializer raises AuthenticationFailed, so the ordinary rejected-login response does not roll them back. Invalid CSRF is rejected before authentication/counter mutation. Unknown accounts perform dummy hashing without creating unbounded guard rows. Database failures propagate rather than allowing login. SQLite is supported only for development; concurrency evidence requires PostgreSQL.

Local full suite: 67 discovered, 53 passed, 14 PostgreSQL-only skipped, 1.242s. Tests cover API+HTML flow, CSRF, fifth failure, exact expiry ±1 microsecond, reset, aliases/admin route and unknown accounts. Two PostgreSQL tests race six initial failures and concurrent correct passwords against an already locked account. Existing login/ownership/session and booking tests remain included. The PR conversation records exact PostgreSQL run/revision/results after execution; no result is predicted here.

Demo: register a disposable account; submit five wrong logins through /login/ or /api/auth/login; correct credentials still fail during lock. Automated reversible-clock tests prove expiry without waiting 15 minutes or changing server time. Do not reset a real user's guard for a demo. No real passwords or verification codes are collected in chat. Full security/load acceptance is separate.
